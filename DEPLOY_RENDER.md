# Deploy Plus One on Render

This path publishes one hosted Plus One instance with PostgreSQL, server-side DeepSeek access, collected static files, and HTTPS through Render. Visitors use the public Render URL and never receive `DEEPSEEK_API_KEY` in the browser.

For an existing deployment, follow the [compatibility rollout sequence](docs/engineering/optimization_delivery_2026-09-19.md) and [paid deployment checklist](docs/engineering/deployment_upgrade_checklist.md) first. Back up and test restoration into an isolated database before production migration. The repository's free-plan configuration does not establish the current account plan or database expiry date.

## 1. Preflight locally

Run these from the Django project root:

```bash
python --version
python -m pip install -r requirements.txt
python -m pip check
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
python manage.py collectstatic --no-input
git diff --check
```

The repository pins Python 3.13 in `.python-version`, matching CI. Render reads
this file automatically; remove or update any conflicting `PYTHON_VERSION`
value already set in the dashboard. See Render's
[Python version guide](https://render.com/docs/python-version).

Make sure real secrets are not committed:

```bash
git status --short
```

The real `.env` file is ignored by git. `.env.example` must contain placeholders only.

## 2. Push to GitHub

Review the intended files, commit them, and push the exact branch configured in
Render. This repository currently delivers from `deepseek-api`; do not switch
an existing service to `main` unless that branch has intentionally become the
release source.

```bash
git status --short
git diff --check
git add --patch
git commit -m "Prepare Plus One for production deploy"
git push origin deepseek-api
```

Stage any reviewed new files separately before committing.

## 3. Create or update the Render service

For a new installation:

1. Open the Render Dashboard.
2. Choose **Blueprints**.
3. Connect the GitHub repository.
4. Select `render.yaml`.
5. When Render asks for `DEEPSEEK_API_KEY`, paste the real key into Render's environment variable UI.

`render.yaml` creates:

- a Python web service named `plusone`,
- a PostgreSQL database named `plusone-db-v2`,
- free instance plans for the first public test,
- a generated `SECRET_KEY`,
- `DJANGO_DEBUG=False`,
- `DATABASE_URL` wired from the Render PostgreSQL database,
- HTTPS redirect and short HSTS defaults in Django production mode,
- `build.sh` as the build command,
- Gunicorn + Uvicorn as the start command.

For the existing hosted product, sync the existing Blueprint or deploy the
existing web service. Do not create another database simply because a resource
name differs in the dashboard. First confirm that the current service keeps its
existing `DATABASE_URL`, database resource and region.

## 4. Confirm environment variables

Render should have:

```text
DEEPSEEK_API_KEY=your_real_key
DEEPSEEK_BASE_URL=https://api.deepseek.com
PLUSONE_LLM_MODEL=deepseek-v4-flash
PLUSONE_MODERATION_MODE=external
PLUSONE_MODERATION_TIMEOUT_SECONDS=5
PLUSONE_INTERACTIVE_TIMEOUT_SECONDS=8
PLUSONE_NEW_MATCHES_ENABLED=false
DJANGO_DEBUG=False
SECRET_KEY=<generated by Render>
DATABASE_URL=<provided by Render PostgreSQL>
SECURE_SSL_REDIRECT=True
SECURE_HSTS_SECONDS=3600
```

`RENDER_EXTERNAL_HOSTNAME` is set automatically by Render and is used by Django for `ALLOWED_HOSTS` and CSRF trusted origins.

Keep new matches disabled while deploying the compatible server, migrations, and static assets. After readiness and smoke checks, set `PLUSONE_NEW_MATCHES_ENABLED=true`. The gate does not stop existing conversations. Missing or unavailable external moderation blocks new content with input preserved; never enable development rules in production. Do not roll back to code that cannot read `WAITING` records.

If you add a custom domain later, add:

```text
ALLOWED_HOSTS=your-domain.com
CSRF_TRUSTED_ORIGINS=https://your-domain.com
```

Only enable these after you are certain every subdomain under your domain is HTTPS-only:

```text
SECURE_HSTS_INCLUDE_SUBDOMAINS=True
SECURE_HSTS_PRELOAD=True
```

## 5. Verify the live app

After the first deploy completes:

1. Confirm `/healthz/` returns `ok` and `/readyz/` confirms database connectivity, then open the `.onrender.com` URL.
2. Create a Plus One card from casual text.
3. Open another browser or private window to simulate a second anonymous user.
4. With new matches enabled, swipe interested and confirm the waiting room does not start with only one participant present. Open both chat pages, send a safe message, agree to meet, and confirm the handoff.
5. Try an unsafe post or chat message and confirm it is blocked.
6. Visit `/dashboard/` and confirm live cards, open chats, handoffs, and history render cleanly.

The scheduled GitHub workflow checks both `/healthz/` and `/readyz/`. A failed
request fails the workflow instead of being converted into a green result.
This probe is not a backup, does not prevent database expiry, and does not prove
that the deployed commit matches the repository branch.

## 6. Production data note

`build.sh` runs migrations only. It does not run `seed_demo`, so production will not be filled with demo users and demo posts.

If you intentionally want a demo environment, run this manually in a non-production database:

```bash
python manage.py seed_demo
```

The free Render Postgres plan is suitable for launch testing, but it has platform limits and may expire according to Render's current free database policy. Upgrade the database before treating user data as durable.

## 7. Rotate the key later

Use a dedicated DeepSeek key for this deployment. If the key is exposed or the review period ends, delete or rotate it in the DeepSeek dashboard and update the Render environment variable.
