本轮复查覆盖 Plus One 的发布、发现、等待、聊天、确认计划、赴约、反馈、举报与回访流程。审查日期为 2026-10-03，页面时间按 Asia/Shanghai 理解。

本文保留审查时的发现与复现结果。后续实施状态和验证记录见[交互修复记录](2026-10-03_interaction_fixes.md)。

当前需要优先解决的是操作结果与用户意图不一致，以及同一计划在不同入口显示不一致。其后再改善赴约协调、等待失败后的恢复和回访提醒。下面区分已复现的问题与需要产品决策的建议；本轮没有修改应用代码、推送 GitHub 或执行部署。

**验证范围与限制**

- 完整浏览器复现使用独立 SQLite 数据库和两个独立访客会话，运行 Chromium，手机视口为 390 × 844。活动仅存在于隔离数据库；未向实际活动列表加入测试活动。
- 浏览器走通手填 → AI 建议 → 校验失败 → 发布 → Interested → 双方进入聊天 → 修改共享计划 → 双方确认 → 赴约页 → 举报 → 查看屏蔽记录。另在真实页面验证标题输入框按 Enter 的默认动作。
- 独立 TestCase 探针完成 7/7 项领域与 HTTP 检查，另一个回访探针完成 1/1。前端补充探针在隔离 Chromium DOM 中执行当前 app.js，包含失联恢复、AI 页面刷新、时间约束及键盘焦点。
- 首轮浏览器检查遇到 SQLite 并发写锁，随后串行运行开发服务器并完成流程；该环境问题没有计为生产缺陷。此轮没有重跑上一轮的完整测试套件，也没有验证 Render 当前线上版本。
- VoiceOver、NVDA、真实手机通知权限和校园真人赴约尚未实测；涉及这些的结论保留验证边界。

**已复现的问题与对应验收**

1. **P1：标题输入框按 Enter 会触发 AI，甚至应用建议覆盖手填内容。**

   新建页输入标题后按 Enter，实际默认提交按钮为 `action=assist`。已有建议时，手填标题“Manual title changed after suggestion”按 Enter 后变为建议“Study sprint”，建议区随即隐藏；用户没有主动点击 Apply。

   证据：真实完整页面 Chromium；[create_post.html](../../plusone/templates/plusone/create_post.html) 第 33、69、76 行，[app.js](../../plusone/static/plusone/app.js) 第 404 行。验收：有无建议、建议区隐藏后、无 JavaScript 四种状态下，Enter 都不能意外调用起草或应用建议；文本域仍正常换行。先确定表单的默认动作，再实现键盘行为。

2. **P1：待核实的发布请求恢复时遮蔽更新的草稿。**

   发布内容 A，响应过程中继续改为 B；断网后刷新，旧请求 A 自动覆盖表单。B 仍存在普通草稿缓存中，但界面没有找回 B 的入口。成功响应路径也直接清除普通草稿，未区分发送后新增的编辑。

   证据：隔离 Chromium 执行真实发布恢复逻辑；[app.js](../../plusone/static/plusone/app.js) 第 467、520、538 行。验收：原请求仍能以同一请求标识和同一 A 核实结果，同时保留 B 的明确恢复入口。发送期间可以锁定编辑，也可以保存独立的后续编辑，不能静默覆盖。用户提示应解释“先确认刚才是否发布成功”，无需用户理解 request ID。

3. **P1：聊天举报没有尊重“同时屏蔽”的勾选。**

   不勾选 `Also block this guest identity` 提交举报，仍创建屏蔽关系。完整浏览器随后在 Updates 中看到 `Unblock this identity`；隔离 HTTP 检查也确认记录存在。

   证据：[views.py](../../plusone/views.py) 第 652 行未传入勾选值，[chat.py](../../plusone/services/chat.py) 第 52 行默认 `block=True`。验收：不勾选仅执行举报自身的安全处理，勾选才额外屏蔽；双方其他未结束关系的后果也要按选择处理。举报表单应按当前阶段披露关闭聊天或取消未结束赴约的后果，无 JavaScript 也要看到说明。

4. **P1：确认前没有完整展示正在同意的计划。**

   共享计划折叠摘要和 Agree 摘要只有地点、开始时间，预计结束时间藏在两层编辑区。对方只改变结束时间时，用户可能直接同意没有看到的新时长。

   证据：静态完整模板 Chromium；[chat.html](../../plusone/templates/plusone/chat.html) 第 53、93 行。验收：确认区始终显示地点、开始—结束时间、当前计划版本的变化；只改结束时间也能不展开编辑区看懂。计划改变仍要求双方重新确认，五分钟时钟不重置。

5. **P1：修改共享计划后，列表仍展示原活动安排。**

   将计划改为“Library north entrance，22:53”后，My Plus Ones 的聊天入口仍显示“Main Library，22:48–23:48”。自己的活动列表又只有时分，无法区分今天和明天。

   证据：真实浏览器与隔离 HTTP；[dashboard.html](../../plusone/templates/plusone/dashboard.html) 第 73、97 行。验收：匹配入口展示该匹配的当前共享计划，原活动信息如保留需明确标注；跨日展示日期，所有入口对地点、开始和结束时间一致。

6. **P2：AI 起草后的刷新重复提交旧请求，并恢复旧字段。**

   起草响应直接渲染 POST 页面。用户之后修改为 B，刷新会重新发送先前的 `POST assist(A)`，返回 A；本地 B 未在界面恢复。每次真实起草 POST 都会重新执行配额、审核和解析。

   证据：隔离浏览器 HTTP 路由模拟确认重复 POST；[views.py](../../plusone/views.py) 第 369–388、463 行确认当前处理路径。未调用真实付费 AI 验证。验收：起草完成后刷新只读 GET，不增加起草调用，保留建议与更新的手填编辑；浏览器返回也不意外重提。

7. **P2：清除草稿的提示与实际行为不一致。**

   AI 返回或校验失败的页面点击 Clear saved draft，提示 `Saved draft discarded.`，标题仍是原提交内容，AI 建议也仍在。原因是 reset 恢复服务器输出的初始值。

   证据：真实完整页面 Chromium；[app.js](../../plusone/static/plusone/app.js) 第 388–399 行。验收：明确选择“仅删除本地保存”或“丢弃并重新填写”的产品含义，按钮文字、当前字段、建议区和刷新后的状态要对应。不能在提示丢弃后又恢复旧提交值。

8. **P2：合法的会面草稿恢复后，被旧日期约束挡住。**

   原会面 18:00，合法提前编辑为 17:50–17:55；恢复草稿后结束输入框 min 仍为 18:00，浏览器报 `rangeUnderflow=true`，后端窗口规则却允许该未来时间。

   证据：组件级 Chromium 和后端规则核对，尚未完整会面页复现；[chat.html](../../plusone/templates/plusone/chat.html) 第 58 行及 app.js 草稿恢复逻辑。验收：草稿恢复、接受最新计划、保留本地编辑后均重算开始和结束的约束，合法时间可直接提交。

9. **P2：屏蔽之后，不同页面对同一关系的状态不一致。**

   公开屏蔽后，直接回 Dashboard 暂时仍有等待或赴约，session polling 后才关闭；屏蔽关闭可能显示“时间耗尽”。回访被屏蔽活动时 Interested 仍可点击，点击却称活动已失效。服务端已经即时禁止新匹配，没有发现绕过屏蔽的新匹配路径。

   证据：隔离 HTTP；[lifecycle.py](../../plusone/services/lifecycle.py) 第 85 行，[views.py](../../plusone/views.py) 第 478 行，[chat.html](../../plusone/templates/plusone/chat.html) 第 101 行。验收：操作完成后 Dashboard、详情、聊天同步收敛；用不泄露举报隐私的准确原因说明关系已结束，提供可执行的下一步。

10. **P2：发现页已显示到期，Interested 仍然可点。**

    停留页面直到倒计时 expired，按钮仍启用；活动窗口比招募截止更早结束时，招募倒计时还可能显示剩余时间。用户点击之后才发现不可匹配。

    证据：静态 Chromium；[discover.html](../../plusone/templates/plusone/discover.html) 第 85、116 行，[app.js](../../plusone/static/plusone/app.js) 第 84 行。验收：按实际可匹配截止更新卡片和按钮，恢复前台立即核对；刷新保留筛选与浏览位置。后台仍需校验其他人刚抢先匹配的竞争场景。

11. **P2：迟到提示缺少明确的到达时间。**

    已比原计划晚 20 分钟，仍可点击“5 min late”；对方只有迟到 5 分钟的文字，没有更新时间或预计几点到。数字相对计划还是当前时间不明确。

    证据：领域与 HTTP 探针；[meetups.py](../../plusone/services/meetups.py) 第 350–354 行。验收：显示预计到达时刻与更新时间，重复更新不会得到已经过去的到达预期；明确“清除迟到”后的状态。

12. **P2：仍可反馈时，回访没有反馈任务。**

    赴约窗口结束且尚在反馈有效期，Updates 可以为空，Dashboard 可以显示 All clear；用户需主动找到 History 才能反馈。

    证据：领域探针；[selectors.py](../../plusone/selectors.py) 第 117–150 行及 [notifications.py](../../plusone/services/notifications.py)。验收：回访显示一次“记录赴约结果”与具体截止时间；提交或过期后移除，保留用户自报与实际到场证明的区别。

13. **P2：轮询更新通知会丢失键盘焦点。**

    聚焦 Needs your attention 的链接，5.4 秒后轮询重建节点，焦点从链接掉到 BODY。用户读到一半再按 Enter 无法打开原目标。

    证据：静态 Chromium 使用真实轮询逻辑；[app.js](../../plusone/static/plusone/app.js) 第 1633 行。验收：按稳定标识更新节点，相同内容不重建；连续三轮相同或新增通知后，聚焦的未删除链接仍可直接打开。

14. **P2：可读性与读屏提醒还需要打磨。**

    青色主按钮白字的实测对比度约 2.13:1，普通文字低于 4.5:1；倒计时在 aria-live 区域每秒变化，存在持续播报风险。

    证据：Chromium 计算样式与 DOM 更新；[styles.css](../../plusone/static/plusone/styles.css) 第 238、2310 行，[chat.html](../../plusone/templates/plusone/chat.html) 第 17 行。验收：关键按钮文字达到适用对比度要求，秒级倒计时不持续播报，只提示重要阶段变化。读屏影响需 VoiceOver/NVDA 实测，手机户外可读性需真人测试。

**需要产品取舍的流程改进**

| 流程 | 当前缺口 | 建议 |
| --- | --- | --- |
| 发布成功 | 主内容只有 Back to Discover 和 Edit；“自己的真实计划发布后如何等人”交接较弱 | 成功页显示招募截止时刻，提供查看等待/匹配入口，以及可选通知设置。未配置后台推送时按实际能力说明，不暗示离开页面必定收到提醒。 |
| 等待超时 | 原活动可以重新开放，但原客人的 Swipe 会排除它；再次 Interested 返回同一个已过期房间 | 决定是否允许主动发起新的尝试。当前一次匹配规则如保留，要明确说明下一步；如新增重试，应是可辨认的新尝试，不能静默延长旧等待或跳过身份/安全/排期检查。 |
| 确认后赴约 | 双方确认后输入框和计划编辑关闭，只剩到达、迟到、取消 | 保留短聊天设定，补充轻量赴约协调，例如“在北门”“找不到你”、预计到达时刻；若支持改变地点/时间，须让双方重新确认。此项属于能力选择，不认定当前关闭聊天的规则为故障。 |
| 手机回访 | 同一计划可同时显示“计划已就绪”“安排已改变”“时间将近”；实测顶部通知挤占首屏，赴约操作需继续下滑 | 让当前阶段的任务优先，历史消息移到 Updates；已完成或被新状态覆盖的行动提示不继续抢占首屏。将 handoff 等内部表达改为用户能理解的“已约好/赴约安排”。 |
| 首次使用 | 当前字段负担是否过重尚无真人证据 | 用真实用户观察是否理解招募截止与活动时间的区别、是否知道匹配会先等待。依据理解成本调整提示和默认值；不以虚拟活动填充列表。 |

建议实施顺序：先修 1–5，保证发布、举报和确认过程符合用户意图；再处理刷新/草稿、过期与屏蔽后的状态一致性；随后完善赴约协调、反馈任务、通知信息层级和可访问性。每批以该段真实交互走通为验收，不以新增功能数量作为完成标准。
